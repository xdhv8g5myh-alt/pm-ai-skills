# PM 代码审查 执行步骤

> 执行前必须 Read `${CLAUDE_SKILL_DIR}/../pm-common/project-management.md` 了解项目管理规范。

## 步骤 0：门禁检查（硬门禁，可强制跳过）

1. `backend/` 存在
   - 不存在 → ❌ 停止：`请先执行 pm-dev-1-backend`
2. 用户强制跳过 → 记 `"dependencySkipped": true`

## 步骤 1：读取上下文

1. 【计划一致性】`design/[项目名]-功能详细设计.md`（核对实现是否符合设计）
2. 【被测对象】`backend/src/main/java` 全量代码
3. 【前端（可选）】`frontend/src/`（存在才审查）
4. 【辅助】`test/*-单元测试报告-*.md`（参考，不作为判定）
5. `.pm-state.json`（读 `devProjectType`）

## 步骤 2：后端审查

### 2.1 编码规范

- 分层是否清晰（controller 不塞业务逻辑、service 不直接操作 HttpServletRequest）
- 命名/包结构是否对齐 DDL（entity `@TableName` 与表名一致）
- `Result<T>` 统一响应、错误码与设计一致、异常统一捕获
- 日志/事务边界（写操作 `@Transactional`）

### 2.2 安全（必查）

- **SQL 注入**：MyBatis-Plus 拼接是否用 `${}` 裸拼、动态 SQL 是否参数化
- **XSS**：回显用户输入是否转义
- **认证授权**：接口是否有鉴权；越权（horizontal/vertical）是否校验数据归属
- **敏感脱敏**：手机号/身份证等出参是否脱敏
- **文件上传**：类型/大小校验、路径穿越防护
- **参数校验**：入参 `@Valid` / 手动校验是否齐全

## 步骤 3：前端审查（可选，前端存在才做）

- API 层 `{code,message,data}` 解包是否正确、错误分支有无提示
- 类型是否对齐响应 schema、无 `any` 滥用
- 敏感信息不硬编码、token 存储方式

## 步骤 4：分级 + 迭代核对

- 分级：严重（必须修复）/ 重要（应当修复）/ 建议（可选）
- 迭代项目额外核对：变更是否破坏既有接口签名、是否引入回归风险、新增代码是否遵守既有约定

## 步骤 5：出报告

写入 `output/[项目名]/review/[项目名]-代码审查报告-[日期].md`：

```markdown
# 代码审查报告

> 批次：[B] | 项目性质：新项目/迭代 | 生成时间：[时间] | 技能：pm-dev-4-codereview v1.4.0

## 一、结论

**严重 [a] 项**（必须修复）· 重要 [b] 项 · 建议 [c] 项

## 二、后端审查

### 严重问题

| 编号 | 位置（文件:行） | 问题 | 代码片段 | 建议改法 |
|------|----------------|------|---------|---------|

### 重要问题 / 建议

（格式同上）

## 三、前端审查（可选）

（格式同上；前端不存在则写"本次无前端产物"）

## 四、修复应答（留空，由修复人填写）

| 编号 | 是否采纳（采纳/不采纳/部分采纳） | 修复说明 | 修复人/日期 |
|------|--------------------------------|---------|------------|
```

## 步骤 6：落盘与更新

### 6.1 更新 .pm-state.json

`devPipeline` 插入/更新 `pm-dev-4-codereview` 条目：
`{"step":"pm-dev-4-codereview","status":"completed","startedAt":null,"completedAt":"…Z","output":"review/[项目名]-代码审查报告-[日期].md","counters":{},"reviewBlockerCount":N}`（N = 严重问题数）。时间戳 UTC 带 `Z`。

### 6.2 更新 README.md

`### 代码审查（pm-dev-4-codereview）` 章节追加一行（5 列：产物/路径/严重问题数/生成时间/批次），
追加在产物清单末尾（`### 变更记录` 之前）。

## 步骤 7：自检

1. 每条问题有 文件:行 + 代码片段 + 建议改法
2. 安全六项（SQL 注入/XSS/认证授权/脱敏/文件上传/参数校验）都查了
3. 严重问题数 = `reviewBlockerCount`，与报告一致
4. 迭代项目兼容性/回归风险已核对
5. 报告落在 `review/`（绝对路径核对过）
6. devPipeline 条目 6+ keys 齐全，时间戳 UTC 带 `Z`
7. README 表 5 列
8. 未修改任何代码

## 步骤 8：会话内输出摘要

只回（不倒全文）：

```
✅ 代码审查报告：`output/[项目名]/review/[项目名]-代码审查报告-[日期].md`

🔴 严重 [a] 项（必须修复）
  - [文件:行] — [一句话说清问题]

🟡 重要 [b] · 🔵 建议 [c]（详见报告）
```
