# PM 评审自查 执行步骤

> 执行前必须 Read `${CLAUDE_SKILL_DIR}/../pm-common/project-management.md` 了解项目管理规范。
>
> 检查项库在同目录 `checklist.md` —— 步骤 3 开始前必须 Read 它。

## 步骤 0：确认评审对象与模式

> **先说清 `output/[项目名]/` 的根在哪**：本技能装在 pm-ai-skills 插件里，
> 但产物在**另一个仓库** —— 含 `output/` 目录的 products 仓库（本机为 `D:\pm-ai\pm-ai-projects`）。
> 当前会话的 cwd 不在 products 仓库时，`output/` 是相对路径**会写错地方**。
> **先定位 products 仓库根，再拼绝对路径。** 定位不到时直接问用户，不要猜。

### 0.1 判断调用模式

| 模式 | 判定 | 差异 |
|------|------|------|
| **嵌入模式** | 由 pm-prd 步骤 3.6 调用 | PRD 路径已知，写完报告即返回，由 pm-prd 回写结论小节 |
| **独立模式** | 用户直接触发（"PRD自查：X"） | 需自己定位 PRD，并更新 README + `.pm-state.json` |

### 0.2 定位评审对象（独立模式）

1. 用户给了项目名 → 取 `output/[项目名]/prd/` 下最新的 `*-PRD-v*.md`
2. 用户给了具体文件路径 → 直接用
3. 都没给 → 列出 `output/` 下的项目让用户选，**不要猜**

> 若 `prd/` 下有多个版本的 PRD（v1.0 / v1.1），**默认评审版本号最高的那个**，
> 并在报告头部注明"本次评审 v1.1；如需评审历史版本请指定"。

### 0.3 确认存在性

评审对象不存在 → ❌ 停止，输出：
```
❌ 未找到可评审的 PRD。
路径：output/[项目名]/prd/
请先执行 pm-prd 生成 PRD，或指定具体文件路径。
```

## 步骤 1：读取上下文（规范引用铁律）

**必须按顺序读取，未读完不得进入步骤 2**：

1. **【主对象】** 评审目标 PRD
2. **【强制的佐证来源】** `output/[项目名]/analysis/analysis-report.md`
   —— 若不存在，**显著提示**："未找到需求分析报告，①需求分析与 ②架构 维度的判定将不完整（这些内容通常不在 PRD 里）"，然后继续，但报告里必须标注该局限
3. `output/[项目名]/prd/[项目名]-test-cases.md` —— A1-6 的判据
4. `output/[项目名]/prd/[项目名]-estimate.md` —— A1-5 的判据
5. `output/[项目名]/project-spec.md` —— 术语一致性的基准
6. `CLAUDE.md`（如存在）

> **铁律**：不要只读 PRD 就开始评审。①需求分析（风险/合规/边界）与 ②架构 大部分在
> 分析报告的第 5 章与第 7 章，不读就会对 A2-1 ~ A2-5 误报 ❌。

## 步骤 2：识别文档结构（语义映射）

**不按编号硬匹配**。真实产出会偏离模板。

1. 提取 PRD 的全部章节标题
2. 判断结构类型：
   - **七章节标准型** → 直接映射
   - **偏离型**（如第六章是「接口需求」而非「运营配置需求」）→ 按章节**含义**映射，把检查项挂到实际存在的章节上
   - **非 pm-prd 产出**（如 `prd-generator` 的页面类型模板）→ 记录"本文档非 pm-prd 七章节格式"，**A1-\* 按实际章节结构映射判定**；确实映射不上的项记 **N/A 并写明"该文档无对应章节"**——不得记 ❌，那是文档形态不同，不是缺陷
3. 把映射结果记下来，报告里要写明本次的章节映射

## 步骤 3：过 A 档（22 项必查）

对 `checklist.md` 的 A1（7 项）+ A2（15 项）逐项判定，每项给：

| 字段 | 要求 |
|------|------|
| 结论 | ✅ / ✅↑ / ❌ / N/A |
| 证据 | **引用 PRD 中的具体章节 + 原文片段**；✅↑ 要写明来源文件与章节 |
| 严重度 | 仅 ❌ 项需要：高 / 中 / 低 |
| 建议改法 | 仅 ❌ 项需要：**可直接粘贴进 PRD 的成稿文字** |

**判定规则**：
- 覆盖在上游文件里 → 记 `✅↑` 并注明来源，**不算缺失**
- 找不到 = 记 ❌，**不得假设"应该写了"**
- 记 N/A 必须写一句为什么

## 步骤 4：判定 B 档激活（11 组）

1. 对 `checklist.md` 的 B1~B11，在 PRD 中检索触发词
2. **触发词是线索不是判据**：既要看字面命中，也要看语义。
   例：PRD 写"上传 Excel 模板"没有"上传"二字，仍算命中 B1
3. 对激活的组逐项检查，格式同步骤 3
4. 对未激活的组，**每组记一行原因**：
   `B7 移动端 —— 未激活（PRD 中无 H5/小程序/移动端相关内容）`

> 不要为了"显得全面"而激活不该激活的组。**未激活并说明原因，比强行激活更有价值。**

## 步骤 5：C 档处理

默认**不展开**。报告末尾给一句提示即可：

```
> C 档归档档（16 项：架构评审 / 立项评审 / 细节完善度）本次未展开。
> 需要深审请说「展开归档档」。
```

用户明确说"展开归档档"时，才逐项检查 C-1 ~ C-16。

## 步骤 6：生成报告

写入 `output/[项目名]/prd/[项目名]-review-[日期].md`（日期格式 `YYYY-MM-DD`）。

**重跑生成新日期文件，不覆盖旧报告**（便于对比两版 PRD 的改进）。

```markdown
# PRD 评审自查报告

> 批次：[当前批次] | 评审对象：`prd/[PRD 文件名]` | 生成时间：[日期时间] | 技能：pm-review v1.0.0
> 佐证来源：analysis-report.md / test-cases.md / estimate.md / project-spec.md
> 章节映射：[说明本次把检查项映射到了实际文档的哪些章节]

## 一、结论

**A 档 22 项**：✅ [N] · ✅↑ [M] · N/A [P] · ❌ [X]　（N + M + P + X = 22）
```

### 报告质量的三条硬要求

1. **每条 ❌ 必须有证据**：引用 PRD 的具体章节 + 原文片段。写不出证据的 ❌ 是臆测，删掉
2. **每条 ❌ 必须有可粘贴的改法**：不是"建议补充异常处理"，而是**直接把该补的那段字写出来**，
   用户复制即可。**落点以"需要改哪个文件"为准**——A1-6 的改法落在 `test-cases.md` 的用例行、
   A1-5 落在 PRD 的工时行，**不要求都粘进 PRD 正文**
3. **结论要能一眼看完**：第一节的结论行是给"只看 10 秒"的人看的，数字必须准确

## 步骤 7：保存与更新

### 7.1 独立模式

**README.md** —— 三件事：

1. 更新索引头的 `> 最后更新：[日期时间]`。这属于**索引维护**，不受
   `project-management.md`「不可手动编辑产物清单之外内容」那条限制（那条禁的是改正文内容）。
2. 在 `### 评审自查（pm-review）` 章节追加一行产物。
   该章节**追加在产物清单末尾**（`### 变更记录` 之前）。**不要插在「PRD 文档」与「前端代码」之间**——
   那会打乱 `project-management.md` 规定的基础模板章节顺序。
3. 基础模板里**没有**这个章节，首次执行时需创建。列结构定为：

   | 产物 | 路径 | Blocker 数 | 生成时间 | 批次 |
   |------|------|-----------|---------|------|

**.pm-state.json** —— 把 `pm-review` 条目**插到 `pm-prd` 条目之后**（即它的逻辑位置），
不是字面 append。`pipeline` 表示执行顺序，直接 append 会写出
`…→ prd → deliver(pending) → review` 的错误顺序，破坏断点续做语义。

> **注意**：若此时所有步骤都已是 `completed`，"插到最后一个 completed 之后"会退化成字面 append。
> 所以位置规则一律以**"紧跟在 `pm-prd` 之后"**为准，不看 completed 状态。

条目内容（保留 `startedAt` 与空的 `counters`，与其它条目形状一致）：

```json
{ "step": "pm-review", "status": "completed", "startedAt": "[时间]", "completedAt": "[时间]",
  "output": "prd/[报告文件名]", "counters": {}, "reviewBlockerCount": N }
```

**project-spec.md** —— **不写**（本技能不产生技术决策）。

### 7.2 嵌入模式

- **不新增** `pipeline` 条目 —— pm-prd 的条目里已有 `reviewBlockerCount`
- README 与 `.pm-state.json` 由 pm-prd 步骤 3.6 统一更新
  （README 同样写入 `### 评审自查（pm-review）` 章节，位置规则同 7.1）
- 本技能只负责产出报告文件

### 7.3 严禁事项

**本技能绝不修改 PRD 本身。** 报告只给建议改法，改不改由用户决定。

理由：AI 自行补写 PRD 会产生看似合理但未经确认的内容，用户不会逐条复核，
最后污染的是下游的原型与代码。

## 步骤 8：输出规则自检

输出前逐项核对：

1. **证据完整性**：每条 ❌ 都有评审对象的章节引用 + 原文片段
2. **改法可粘贴**：每条 ❌ 的建议都是成稿文字，不是"建议补充…"
3. **无脑补**：不存在的章节没有被当成"已写"；不确定的判为 ❌ 而非 ✅
4. **覆盖口径统一**：`✅↑` 只给了 `analysis-report.md` 与 `project-spec.md`；
   只写在 `test-cases.md` / `estimate.md` 里的内容仍记 ❌（并注明"仅见于 test-cases"）
5. **未误报结构**：偏离模板的章节（如「接口需求」）**没有**被判为"章节缺失"
6. **B 档激活合理**：字面命中但语义不相关的组（如"手机号"之于 B7）**没有**被激活；
   每个未激活的组都写了原因；也没有为了全面而强行激活
7. **Blocker 门槛**：Blocker ≤ 5；每一条都满足两条硬门槛之一
   （①开发会做错 ②上线必然整改），**合规/安全类缺陷走门槛 ②**，不得因"不是开发写错代码"而降级
8. **计数已去重**：A/B 档同义项按计数规则只计一次，且被去重项都带 `（不重复计数）` 字面脚注
9. **N/A 有理由**：每个 N/A 都写了为什么该形态不适用，且没有用 N/A 逃避本该判 ❌ 的项
10. **路径正确**：报告写在 products 仓库的 `output/[项目名]/prd/` 下（用绝对路径核对过）
11. **只读未改**：PRD / 测试用例 / 工时估算 / analysis-report **均未被修改**
12. **数字自洽**：结论行 ✅ + ✅↑ + N/A + ❌ = 22；Blocker/建议/提示 与正文明细一致

## 步骤 9：会话内输出摘要

报告写完后，在会话里只回这些（**不要把报告全文倒出来**）：

```
✅ 评审报告：`output/[项目名]/prd/[项目名]-review-[日期].md`

必查 22 项：✅ [N] · ✅↑ [M] · N/A [P] · ❌ [X]
条件触发：激活 [K]/11 组，未激活 [11-K] 组 — [列出组号，如 B7、B8]

🔴 Blocker [a] 项（须评审前解决）
  - [检查项] — [一句话说清缺什么]

🟡 建议 [b] 项 · 🔵 提示 [c] 项（详见报告）
```

**未激活的组必须出现在摘要里**（只列组号即可）——否则用户不知道哪些角度没查过，
会误以为报告已经覆盖全部 11 组。

Blocker 每项一行，说清**缺什么**，不复述建议改法（那是报告里的事）。
