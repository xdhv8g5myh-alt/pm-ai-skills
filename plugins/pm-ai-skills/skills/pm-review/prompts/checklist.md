# PRD 评审自查 · 检查清单

> 本文件是 `pm-review` 的检查项库。执行步骤见同目录 `prompt.md`。

## 三档的含义

| 档位 | 何时检查 | 报告里怎么体现 |
|------|---------|---------------|
| **A 档 · 必查**（22 项） | 任何 PRD 都要过，逐项给结论 | 全部列出，✅/❌ 都要写 |
| **B 档 · 条件触发**（11 组） | 由 PRD 的实际内容激活 | 只列激活的组；未激活的记一行原因 |
| **C 档 · 归档**（16 项） | 默认不展开 | 报告末尾提示"说展开归档档可深审" |

**默认一次只过 A 档 22 项 + B 档被激活的组。** 这是"不淹人"的关键——不要 98 项全量铺开。

---

## 评审前必读

### 评审对象不止 PRD 一个文件

按顺序读：

| # | 文件 | 作用 |
|---|------|------|
| 1 | `output/[项目名]/prd/[项目名]-PRD-*.md` | 主评审对象 |
| 2 | `output/[项目名]/analysis/analysis-report.md` | **必需的佐证来源** |
| 3 | `output/[项目名]/prd/[项目名]-test-cases.md` | A1-6 的判据来源 |
| 4 | `output/[项目名]/prd/[项目名]-estimate.md` | A1-5 的判据来源 |
| 5 | `output/[项目名]/project-spec.md` | 术语一致性的基准 |

> **为什么必须读分析报告**：①需求分析（风险 / 合规 / 边界）和 ②架构 有很大一部分**不在 PRD 里**，
> 而在分析报告的**第 5 章（系统边界）**和**第 7 章（待澄清问题 + 风险等级）**。
> 只看 PRD 会对这些项误报 ❌。
>
> **规则：覆盖在分析报告里 = ✅，并注明来源**，如 `✅ 来源：analysis-report.md 第 7 章 #3`。

### 哪些算"覆盖来源"（口径必须统一）

| 文件 | 算覆盖来源？ | 说明 |
|------|-------------|------|
| `analysis-report.md` | ✅ 是 | 可记 `✅↑` 并注明章节 |
| `project-spec.md` | ✅ 是 | 可记 `✅↑` 并注明来源（技术决策/术语表/接口清单） |
| `test-cases.md` | ❌ **否** | 只是 A1-6 的**判据来源** |
| `estimate.md` | ❌ **否** | 只是 A1-5 的**判据来源** |
| `CLAUDE.md` | ❌ 否 | 是生成时的约束，不是覆盖 |

> **为什么测试用例不算覆盖**：PRD 是开发唯一会读的交付物。某个空态或限制提示
> **只写在测试用例里、PRD 正文没写**，那就是 PRD 的缺口——仍记 ❌，
> 但在证据里注明 `仅见于 test-cases.md T037`，方便判断该补进 PRD 哪一节。
>
> 不写死这条口径，每个执行者都会自行发明一套，报告之间就没法比了。

### 章节按语义映射，不按编号

实测产出会偏离模板——例如真实 PRD 的**第六章是「接口需求」**，而模板写的是「运营配置需求」。
先识别文档的实际章节结构，再把检查项映射上去。**不按编号硬匹配。**

### 查"写没写"价值低，查"写得够不够用"价值高

模板已经保证的章节（验收标准、数据字典、性能、权限）**不查存在性，只查实质内容是否到位**。
问"有没有验收标准"是噪音；问"验收标准能不能量化验收"才有用。

## 判定符号

| 符号 | 含义 |
|------|------|
| ✅ | 已覆盖且实质可用 |
| ✅↑ | 由上游文件（分析报告 / project-spec）覆盖，注明来源 |
| ❌ | 缺失或实质不足 |
| N/A | 本次需求确实不涉及（**必须写一句为什么**） |

> **N/A 在 A / B / C 三档都可用**，不止 A2。凡"该检查项对本次需求的形态不适用"即可记 N/A，
> **但必须写一句为什么**。
>
> 例：B2-5「字数上限的临近提示」对"Excel 离线填写"这种输入形态不适用（系统看不到输入过程）；
> A1-3「组件绑定」对**前端 0 天的纯后端功能点**不适用（无 UI 可绑组件）。
>
> **不得用 N/A 逃避本该判 ❌ 的项。** 判断标准：是"这项对本次需求没有意义"（→ N/A），
> 还是"这项有意义但文档没写"（→ ❌）。

## 严重度

沿用 `analysis-report.md` 第 7 章的 **高 / 中 / 低** 词汇以保持一致。
但注意：第 7 章的等级绑在"待澄清问题"上，与本清单发现的缺陷不是一回事，
**判据以下表为准**，不要去第 7 章找对应表。

| 严重度 | 判定标准 | 报告去向 |
|--------|---------|---------|
| **高（Blocker）** | 满足下方**任一条**硬门槛 | 第二章，须评审前解决 |
| **中（建议）** | 会影响实现质量或后期维护，但开发按现有 PRD 也能做对 | 第三章 |
| **低（提示）** | 完善度问题，可以下一版再补 | 第四章 |

### Blocker 的硬性门槛

满足以下**任一条**即可记为 Blocker，两条都不满足则不得记：

| # | 门槛 | 一句话判据 |
|---|------|-----------|
| 1 | **开发会做错** | 不补这条，开发照现有 PRD 写出来的一定是错的，或必然返工 |
| 2 | **上线必然整改** | 不补这条，上线后必然产生合规 / 法务整改、数据泄露或用户投诉 |

**门槛 2 必须存在，不能只留门槛 1。** 只用开发视角会漏掉最该拦的东西——
"身份证明文入库""采集个人信息无授权依据"这类缺陷不是"开发写错代码"，
而是"写出来就有法律暴露"。若只按门槛 1 判定，它们会被降级成「建议」，
而「建议」的定义是"开发按现有 PRD 也能做对"——等于把最严重的放走了。

**"评审上会被问住"不算判据**——几乎所有项都符合这句话。

**Blocker 总数 ≤ 5。** 超过 5 条说明判定太松，回去重判。
一份 PRD 通常 0-3 条真 Blocker；如果每次都报 10 条，这个数字就没人看了。

## 计数规则（避免数字虚高）

**总则（先看这条）**：**凡"改法落在同一段文字"的项，即为同一缺陷。**

这是唯一的裁决依据——不要凭"这两项名字像"来判断。

**计数方式**：同一缺陷**只在其最靠前的检查项上计数**，其余项照记 ❌ 但不计入
Blocker/建议/提示 总数，并加脚注 `同 X-XX（不重复计数）`（**用括号，字面如此**，
便于 grep 核对）。这样结论行的数字才与"实际要改几处"对得上。

**已知的同义项**（不完整，以总则为准）：

| 组 | 同义项 | 共同的改法落点 |
|----|--------|---------------|
| 权限 | A2-6 ↔ B11-1 / B11-2 / B11-3 | 角色—权限—功能矩阵那一段 |
| 外部依赖 | A2-2 ↔ B9-1 / B9-3 | 依赖清单与降级方案那一段 |
| 失败处理 | A2-7 / A2-8 / A2-9 与 B5-4 | **条件性**：仅当改法落在同一段失败态描述上才合并 |

> 最后一行是条件性的：A2-7/A2-8/A2-9 各自独立时**分别计数**；
> 只有当它们的改法要写进同一段文字时才合并。判断依据仍是总则。

# A 档 · 必查（22 项）

## A1 结构完整性（7 项）

> 本节查**结构与实质**。除 **A1-1** 外，各项都只查实质——不问"有没有这个章节"，
> 问"这节写得够不够用"。**A1-1 是本节唯一的存在性检查，必须做。**

| 编号 | 检查项 | ❌ 判据 |
|------|--------|--------|
| A1-1 | 章节齐全且无占位 | 存在 `待补充` / `TBD` / `TODO` / 空表格 / 只有标题没有正文 |
| A1-2 | F 编号一致 | 与 `analysis-report.md` 的 F 编号对不上，或有跳号、重号 |
| A1-3 | 组件绑定 | 功能点未标注 Arco Design Vue 组件名（`ATable` / `AForm` 等）。**前端 0 天的纯后端功能点记 N/A**（无 UI 可绑组件） |
| A1-4 | 优先级 | 功能点无 P0/P1/P2 标注，或全标 P0（等于没排） |
| A1-5 | 工时是范围值 | 写成单点值（`4天`）而非范围值（`3-5天`） |
| A1-6 | 测试用例三维覆盖 | 功能点缺少 正常/边界/异常 任一条；T 编号未关联 F 编号 |
| A1-7 | 验收标准可量化 | 写成"运行正常""体验良好"这类无法验收的空话 |

## A2 需求实质（15 项）

> 这 15 项是模板**不保证**的，也是本清单的主要价值所在。

| 编号 | 检查项 | ❌ 判据 |
|------|--------|--------|
| A2-1 | 对现有业务的影响面 | 未说明本需求会影响哪些已有功能/流程/数据 |
| A2-2 | 外部依赖及其稳定性 | 只列了依赖名，未说明依赖方稳定性、不可用时的降级方案 |
| A2-3 | 合规：数据安全与隐私 | 涉及用户数据却未说明采集范围、存储、脱敏、授权依据 |
| A2-4 | 合规：法律风险 | 涉及资质、合同、对外承诺却未提法律合规确认 |
| A2-5 | 系统边界 | 未写清"本期做 / 本期不做"；或与 `analysis-report.md` 第 5 章不一致 |
| A2-6 | 角色—权限—功能对应 | 有角色定义，但没说每个角色能进哪些功能 |
| A2-7 | 流程级异常与分支 | 只有单功能级的「异常处理」，主流程层面没有异常/分支流程 |
| A2-8 | 逆向闭合 | 反向走一遍流程，取消 / 中断 / 超时 / 回退时不闭合（状态悬空） |
| A2-9 | 出错后的恢复途径 | 用户操作失败后，PRD 没说怎么回到正常状态 |
| A2-10 | 术语一致 | 同一概念在 PRD 内多处用词不一致（如"客户"/"大客户"/"企业客户"混用） |
| A2-11 | 空数据文案 + 引导 | 列表/表格只写了有数据的样子，空态无文案、无引导操作 |
| A2-12 | 超长数据布局 | 未说明字段超长（长名称、长描述、长数字）时如何展示 |
| A2-13 | 跳转目标有效 | 链接/跳转指向不明，或会因版本迭代失效 |
| A2-14 | 数据迁移 / 兼容旧数据 | 有存量数据却未说明迁移或兼容方案 |
| A2-15 | 上线方案 | 未说明灰度 / 全量 / 开关控制策略 |

> A2-14 在**无存量数据**时记 N/A；A2-3 / A2-4 在**确实不涉及**时记 N/A。
> 其余项记 N/A 需按上方「判定符号」的规则给出理由。

### A2-5 的裁决规则

A2-5 同时被"覆盖口径"和"内容一致性"两条规则拉扯（PRD 写了简版、分析报告写了全版时，
一条说记 ✅↑、一条说记 ❌），必须给 tie-breaker：

| 情形 | 判定 |
|------|------|
| PRD **完全未声明**系统边界 | `✅↑` —— 由 `analysis-report.md` 第 5 章覆盖 |
| PRD **声明了但比分析报告窄**（漏了其中某项） | `❌ 低` —— 注明漏了哪一项 |
| PRD 声明与**分析报告冲突** | `❌ 高` —— 开发会按错的那份做 |

# B 档 · 条件触发（11 组）

> **触发方式（两步，缺一不可）**：
> 1. **字面命中** —— 在 PRD 中检索该组触发词
> 2. **语义复核** —— 命中后判断该内容是否属于**本次需求的范围**
>
> **只有两步都通过才激活。** 字面命中但语义不相关时**不激活**，并在报告里记原因。
>
> **反向也要防漏**：PRD 写"上传 Excel 模板"，虽无"上传"二字，语义命中 B1 → 激活。
>
> **真实踩过的坑**：某 PRD 里"手机号"出现 9 次、"小程序"出现 3 次，字面完全命中 B7 移动端——
> 但那些指的是**已有员工端**，本次改动只在 PC 管理后台，语义复核不通过 → **B7 不激活**。
> 同理"状态"出现 20+ 次，但全是只读的数据状态枚举，无 Switch / 启用禁用 → **B8 不激活**。
> 若按"命中即激活"执行，这两组会被误报，报告的可信度就没了。
>
> **未激活的组**在报告里记一行原因：
> `B7 移动端 —— 未激活（"手机/小程序"仅指已有员工端，本次仅 PC 后台）`

## B1 文件上传

**触发词**：上传、导入文件、附件、图片、Upload、Excel、模板下载

| 编号 | 检查项 |
|------|--------|
| B1-1 | 是否提供上传前的预览（图片类必须） |
| B1-2 | 是否有上传进度 / 结果的交互反馈 |
| B1-3 | 上传规则（格式、大小、数量上限）是否明确告知用户 |
| B1-4 | 上传失败（格式错、超限、网络断）的处理与重试 |

## B2 表单输入

**触发词**：表单、新增、编辑、输入、填写、Input、Form、字段说明

| 编号 | 检查项 |
|------|--------|
| B2-1 | 每个字段的**输入来源**（用户手填 / 系统自动 / 接口传入）是否标注 |
| B2-2 | 各字段是否标注是否必填 |
| B2-3 | 校验规则（格式、长度、范围）是否明确，错误提示文案是否给出 |
| B2-4 | 超长输入的截断或提示处理 |
| B2-5 | 字数上限的**临近提示**（如限 200 字，接近上限时是否提示） |

## B3 列表 / 表格

**触发词**：列表、表格、Table、分页、查询、筛选、排序

| 编号 | 检查项 |
|------|--------|
| B3-1 | 表格列名、宽度、对齐方式是否明确 |
| B3-2 | 默认排序字段与排序规则是否明确 |
| B3-3 | 分页默认条数与可选项（如 10/20/50） |
| B3-4 | 特殊数据需要过滤 / 高亮的场景是否标注 |
| B3-5 | 行内操作与批量操作分别是什么、有无二次确认 |

## B4 大数据量 / 导出 / 批量

**触发词**：导出、批量、大量、几万条、全量、异步任务

| 编号 | 检查项 |
|------|--------|
| B4-1 | 数据量大时的处理方案（分页 / 无限滚动 / 提示） |
| B4-2 | 导出是"当前筛选"还是"全量"，是否有条数上限 |
| B4-3 | 批量操作的上限，以及**部分失败**时怎么处理 |
| B4-4 | 长耗时任务是否异步 + 进度反馈 + 完成后如何通知 |
| B4-5 | 系统资源不足时的降级方案 |

## B5 接口 / 异步

**触发词**：接口、请求、异步、轮询、回调、接口需求

| 编号 | 检查项 |
|------|--------|
| B5-1 | 每个数据交互点是否有 loading 态说明 |
| B5-2 | 请求超时与重试机制 |
| B5-3 | 弱网 / 断网下的加载行为 |
| B5-4 | 异步操作失败对页面状态的影响（是否需要回滚） |
| B5-5 | 成功 / 失败的用户反馈文案是否写出 |

## B6 通知 / 推送

**触发词**：通知、推送、消息、提醒、告警、站内信

| 编号 | 检查项 |
|------|--------|
| B6-1 | 触发条件（什么情况下发） |
| B6-2 | 通知内容（发什么） |
| B6-3 | 发送频率与去重，**防重 / 幂等**处理 |
| B6-4 | 用户能否关闭，以及关闭后如何恢复 |

## B7 移动端 / H5

**触发词**：移动端、H5、小程序、手机、App、适配

| 编号 | 检查项 |
|------|--------|
| B7-1 | 不同分辨率（PC / Pad / Mobile）下的显示方案 |
| B7-2 | 软键盘弹出是否遮挡输入框或提交按钮 |
| B7-3 | 浏览器自动填充对输入框的影响 |
| B7-4 | 触屏无 hover，依赖 hover 的交互是否有替代方案 |

## B8 状态切换 / 开关

**触发词**：开关、启用、禁用、状态、Switch、切换、立即生效

| 编号 | 检查项 |
|------|--------|

## B9 依赖外部系统

| 编号 | 检查项 |

| B9-2 | 依赖数据更新时，本页面能否感知并同步 |

## B10 埋点 / 统计

| 编号 | 检查项 |
|------|--------|

| B10-2 | 统计口径是否明确（算的是次数还是人数、去不去重） |
| B10-3 | 功能启动 / 关闭的开关机制是否设计 |

## B11 分角色权限

| 编号 | 检查项 |
|------|--------|
