# PM 设计稿反推需求 执行步骤

> 执行前必须 Read `${CLAUDE_SKILL_DIR}/../pm-common/project-management.md` 了解项目管理规范。

## 步骤 0：初始化项目骨架

1. 询问或确认项目名称
2. 检查 `output/[项目名]/` 是否存在：
   - **不存在**：创建目录骨架
     ```
     output/[项目名]/
     ├── README.md          （用初始模板）
     ├── 项目规范.md    （用初始模板）
     ├── .pm-state.json     （初始化，batch=B1, counters全0）
     └── 需求分析/           （空目录）
     ```
   - **已存在**：Read `.pm-state.json`，获取当前批次和 F 计数器

> **骨架范围收窄**：本技能自建的骨架**仅限** `需求分析/`、`README.md`、`.pm-state.json`、
> `项目规范.md` 四项；**不创建其它产物目录**（`原型/`、`需求文档/`、`设计/` 等由各自技能负责创建）。

## 步骤 1：读取项目上下文（规范引用铁律）

执行任何反推前，**必须按以下顺序读取上下文**（未读取不得进入步骤 2）：

1. **【强制】** Read `output/[项目名]/项目规范.md`（如存在），提取：已有技术决策、业务术语表、接口清单、组件约定
2. Read `CLAUDE.md`（如存在），提取：技术栈、业务术语、已有功能模块（避免反推出已存在的功能）
3. 检查 `需求分析/` 下是否已有 `需求分析报告.md`：
   - **有** → 本技能产出为**补充**，命名 `设计稿反推-[日期].md`，在报告开头标注"本文档为设计稿反推补充，原分析报告见 需求分析报告.md"
   - **无** → 正常产出
4. 如无上下文文件，跳过此步骤继续

## 步骤 2：识别设计稿输入源

| 输入类型 | 识别方式 | 处理方法 |
|---------|---------|---------|
| 设计稿图片 | .png/.jpg/.jpeg/.webp | Read 多模态识别，提取布局、元素、文字、状态 |
| 已有 HTML 页面 | .html | Read 解析 DOM 结构与组件（比图片更精确，优先） |
| 设计稿导出包 | .zip 或目录 | 列出图片清单，逐页 Read |
| Figma / Axure / Sketch 源文件 | .fig/.rp/.sketch | **无法直接解析**，提示用户导出为图片或 HTML 后再执行 |
| 设计稿链接 | http(s):// | **无法抓取**（需登录/鉴权），提示用户提供导出图 |

> 输入不可解析时，明确告知用户并提供导出指引（Figma：选中画板 → Export → PNG 2x；Axure：发布为 HTML），**不得凭链接或文件名猜测内容**。

## 步骤 3：逐页解析界面结构

对每个页面输出：

```markdown
### 页面：[页面名]（来源：[文件名]）

| 区块 | 元素 | 类型 | 画出的状态 |
|------|------|------|-----------|
| 顶部筛选区 | 关键词输入框 | Input | 默认 |
| 顶部筛选区 | 状态下拉 | Select | 默认 |
| 数据表格 | 列表 | Table | 有数据 |
| 表格行操作 | 编辑 / 删除 | Button | 默认 |

**页面级观察**：布局类型（列表页/表单页/详情页）、导航结构、响应式线索
```

**只为画面上真实存在的东西建档。** 看不清的元素标注"待确认"，不得猜测其功能。

## 步骤 4：反推功能点

**这是本技能的核心，也是最需要克制的一步。**

### 4.1 三类信息严格分开

| 类型 | 定义 | 去向 |
|------|------|------|
| **确定的** | 画面上直接可见（元素存在、文字内容、画出的状态） | 功能清单 |
| **推断的** | 由可见元素合理推出（如"有删除按钮 → 需要删除功能"） | 功能清单，**必须标依据 + 置信度** |
| **未知的** | 设计稿无法体现（规则、权限、异常、数据来源） | 待澄清问题 |

### 4.2 置信度判定

| 置信度 | 判据 | 处理 |
|--------|------|------|
| 高 | 画面上有明确对应元素且语义无歧义 | 进功能清单 |
| 中 | 有对应元素但具体规则不明（如"有搜索框，但搜哪些字段不确定"） | 进功能清单，规则部分同时进待澄清 |
| 低 | 纯靠联想，画面上无直接支撑 | **只进待澄清问题**，不进清单 |

### 4.3 反推功能点格式

```markdown
- [ ] **F013 用户列表导出**：导出当前筛选结果为文件。
  *依据：列表页右上角"导出"按钮* | *置信度：高* | *理由：有明确操作入口*
  *待确认：导出格式（Excel/CSV）与是否异步*
```

### 4.4 强制列入待澄清的问题

以下内容设计稿**天然无法体现**，必须逐项列入待澄清问题，不得臆造：

- 空态 / 加载态 / 错误态 / 超限提示
- 权限与角色差异（谁能看、谁能改）
- 数据来源与刷新机制
- 校验规则与边界值
- 与其他模块的联动
- 分页 / 排序 / 默认排序字段

## 步骤 5：输出报告

```markdown
# [项目名称] 设计稿反推需求报告
> 反推日期：[日期] | 输入：[设计稿文件清单] | 技能：pm-design-reverse v1.5.0

## 1. 反推说明
（输入了什么、覆盖哪些页面、哪些页面未覆盖、未覆盖的原因）

## 2. 界面清单
（步骤 3 的逐页结构表）

## 3. 反推功能清单（MoSCoW）
### Must Have（必须做）
- [ ] **FXXX [功能名]**：[描述]。*依据：[画面元素]* | *置信度：高* | *理由：[为什么是 Must]*
### Should Have / Could Have / Won't Have
（同上格式）

## 4. 待澄清问题清单
| # | 问题 | 影响范围 | 风险等级 | 建议决策人 |
|---|------|---------|---------|----------|

## 5. 与已有分析的差异（仅当已有 需求分析报告.md）
| 类型 | 内容 |
|------|------|
| 新增 | 原分析未覆盖、设计稿反推出的功能 |
| 冲突 | 与原分析不一致处（标注双方说法） |
| 补充 | 原分析有但设计稿给出了具体形态的 |

## 6. 下一步建议
1. 【澄清】将待澄清问题（第 4 节）提交干系人确认
2. 【PRD】确认后使用 pm-prd 生成完整产品需求文档
3. 【原型】如需可交互原型，使用 pm-prototype（本技能不生成原型）
```

## 步骤 6：门禁、保存与更新

### 6.1 Blocker 检查

统计待澄清问题中风险等级="高"的数量：
- **> 0** → 报告末尾醒目输出 Blocker 清单，并在 `.pm-state.json` **顶层**记录 `designReverseBlockerCount`
  （本技能**无 `pipeline` 条目**，**不要**把该字段写进别人的条目里；用 `designReverseBlockerCount`
  这个专用 key，避免与 pm-design-3-review 的 `blockerCount` 同名冲突）
- **= 0** → 正常完成

### 6.2 保存

写入 `output/[项目名]/需求分析/设计稿反推-[日期].md`，头部追加：

```
> 批次：[当前批次] | 生成时间：[日期时间] | 技能：pm-design-reverse v1.5.0 | 输入：[设计稿文件清单]
```

### 6.3 更新项目管理文件

- **README.md**：在「需求分析（pm-analyze）」表格的**现有 4 列**（`| 产物 | 路径 | 生成时间 | 批次 |`）
  中追加本次产物行，**不新增「备注」列**；产物名直接写 `设计稿反推-[日期]` 即可自明来源
- **.pm-state.json**：更新 `counters.F` 为最后一个 F 编号的数字（与 pm-analyze **共用 F 计数器，跨批次不重置**）；
  **不修改 pm-analyze 的 status**（本技能不代替 pm-analyze 完成分析）
- **项目规范.md**：若 pm-analyze 未跑过、且本次反推产生了技术决策，则 **append** 到「技术决策」节（不覆盖既有行）。
  **项目规范.md 的首次初始化是 pm-analyze 的职责**，本技能不负责创建它

## 步骤 7：输出规则检查（自检）

输出前自检以下各项：

1. **依据完整性**：每条反推功能点都有 `依据：` 和 `置信度：`
2. **防脑补检查**：功能清单中**不存在**置信度=低 的条目
3. **状态覆盖检查**：空态/加载态/错误态/权限/校验规则 均已列入待澄清
4. **不覆盖检查**：已有 `需求分析报告.md` 未被修改
5. **编号连续性**：F 编号与既有计数器连续，无跳号、无重号
6. **来源可溯**：每条功能点可追溯到具体设计稿文件与画面元素
