# PM 设计评审（五位一体） 执行步骤

> 执行前必须 Read `${CLAUDE_SKILL_DIR}/../pm-common/project-management.md` 了解项目管理规范。
> 检查项库在同目录 `checklist.md`，步骤 3 开始前必须 Read 它。

## 步骤 0：产物依赖门禁（硬门禁，可强制跳过）

1. 检查必需产物：`设计/[项目名]-功能详细设计.md` **和** `设计/数据库/[项目名]-表结构.sql`（或 增量 SQL）都存在
   - 缺任一 → ❌ 停止：`请先完成功能详细设计与数据库设计`
2. `设计/[项目名]-数据库设计.md`（或 `设计/[项目名]-数据库变更设计.md`）**缺失不阻断**：仅据 SQL 评审，并在报告中记一条 Question（与步骤 1 读取清单第 2 条同口径）
3. 检查 `.pm-state.json` 中 `pm-design-1-func`、`pm-design-2-db` 均 `completed`
4. 用户强制跳过 → 记 `"dependencySkipped": true`（写入**本步 `devPipeline` 条目内**）

## 步骤 1：读取上下文

按顺序读取：

1. 【主对象】`设计/[项目名]-功能详细设计.md`（接口设计块 + 字段溯源表）
2. 【主对象】`设计/[项目名]-数据库设计.md`（或 数据库变更设计.md）+ `设计/数据库/*-表结构.sql`（或 增量 SQL）；`.md` 缺失则**仅据 SQL 评审并记 Question**
3. 佐证：`需求文档/*-PRD-*.md`（需求依据）、`原型/[端]/*.html`（UIUE 依据，存在则读）
4. `output/[项目名]/项目规范.md`（约定基准）
5. `.pm-state.json`（读 `devProjectType`，判断是否迭代项目）

## 步骤 2：判定迭代维度

- `devProjectType == "iteration"` → 额外核对 checklist.md「迭代项目额外核对」E-1/E-2/E-3
- `new` → 只过五个维度

## 步骤 3：过五位一体 checklist

对 checklist.md 的 D1~D5（+ 迭代时 E1~E3）逐项判定，每项给：

| 字段 | 要求 |
|------|------|
| 结论 | ✅ / ❌ / N/A |
| 证据 | 引用功能详细设计 / DDL 的具体位置 + 原文 |
| 级别 | 仅 ❌ 项：Blocker / Major / Minor / Question |
| 建议改法 | 仅 ❌ 项：可直接落进设计/DDL 的成稿文字 |

判定规则：找不到 = ❌（缺失），不假设"应该写了"；N/A 必须写原因。

## 步骤 4：生成报告

写入 `output/[项目名]/设计/评审/[项目名]-设计评审-[日期].md`（日期 `YYYY-MM-DD`，重跑生成新日期文件）。

```markdown
# 设计评审报告（五位一体）

> 批次：[B] | 评审对象：`设计/[项目名]-功能详细设计.md` + `设计/数据库/*-表结构.sql` | 生成时间：[时间] | 技能：pm-design-3-review v1.5.0
> 项目性质：新项目 / 迭代
> Blocker 遗留（状态=待确认）：[N]

## 一、结论

五维：字段溯源 / 连通性 / 状态并发 / 性能 / 合规（+ 迭代兼容性）

**Blocker [a] 项**（须评审前解决）· Major [b] 项 · Minor [c] 项 · Question [d] 项

## 二、Blocker（须开发前解决）

| 编号 | 维度 | 现状（位置 + 原文） | 建议改法（可粘贴） | 状态 |
|------|------|--------------------|--------------------|------|

> 「状态」取值 `待确认 / 已确认 / 已关闭`，**默认「待确认」**。重跑时读**上一份报告**回填已标注状态。
> `blockerCount` 只统计**状态为「待确认」**的行（＝报告头「Blocker 遗留」数）。
> 下游（pm-dev-1-backend / pm-dev-autopilot）据此判定是否解除暂停：Blocker 改完后须把状态改「已关闭」（或「已确认」），**重跑本技能生成新报告**后遗留数才会归零。

## 三、Major / 四、Minor / 五、Question

（格式同上）

## 六、逐项结论

| 编号 | 维度 | 结论 | 证据 / 级别 | 状态 |
|------|------|------|------------|------|

> 「状态」列与「二、Blocker」表**同源**：Blocker 行取其状态，非 Blocker 行留空。
```

三条硬要求：每条 ❌ 有证据；每条 ❌ 有可粘贴改法；结论行数字准确。

## 步骤 5：落盘与更新

### 5.1 更新 .pm-state.json

`devPipeline` 插入/更新 `pm-design-3-review` 条目（splice，重跑先摘旧条目）：
`{"step":"pm-design-3-review","status":"completed","startedAt":"…Z","completedAt":"…Z","output":"设计/评审/[项目名]-设计评审-[日期].md","counters":{},"blockerCount":N}`。时间戳 UTC 带 `Z`。
`blockerCount` = 报告「二、Blocker」表中**状态为「待确认」**的行数（＝报告头「Blocker 遗留」数）。

### 5.2 更新 README.md

`### 设计评审（pm-design-3-review）` 章节追加一行（5 列：产物/路径/Blocker 数/生成时间/批次），
追加在产物清单末尾（`### 变更记录` 之前）。

### 5.3 项目规范.md

不写（本技能不产生技术决策）。若评审中发现通用约定（如统一脱敏规则），**提示用户另行沉淀**，不要自行写入。

## 步骤 6：自检

1. 五个维度都过了，未漏维度
2. 每条 ❌ 有证据 + 可粘贴改法
3. Blocker ≤ 5，每条满足「开发会做错/上线必然整改」门槛
4. 迭代项目 E-1/E-2/E-3 已核对
5. 报告落在 `设计/评审/`（绝对路径核对过）
6. devPipeline 条目 6+ keys 齐全，时间戳 UTC 带 `Z`；`blockerCount` = 报告「Blocker 遗留（状态=待确认）」数，与报告一致
7. README 表 5 列
8. 未修改功能详细设计 / DDL / PRD
