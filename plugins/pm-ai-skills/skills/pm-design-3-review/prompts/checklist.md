# 五位一体设计评审检查项

> 本文件是 pm-design-3-review 的检查项库。步骤 3 开始前必须 Read 它。
> 五个维度都要过，每条 ❌ 必须带证据（引用功能详细设计 / DDL 的位置 + 原文）与可粘贴改法。

## 维度一：字段溯源

设计里的每个字段都要能在 DDL 里落地，DDL 的每个字段都要能回溯到需求/PRD。

- **D1-1 需求字段全落地**：PRD/功能详细设计的每个字段，DDL 都有对应列。表存在但字段缺失 = Blocker
- **D1-2 DDL 字段可回溯**：DDL 每个列都能对应到需求/PRD 字段（无来由的冗余列 = Major）
- **D1-3 类型一致**：需求字段类型与 DDL 列类型一致（如 PRD 写 enum 但 DDL 存 varchar 未约束 = Major）
- **D1-4 映射表齐全**：有「PRD 字段 → DDL 字段」映射表，命名转换有据可查

## 维度二：连通性

查询/筛选/关联字段要有对应的 DDL 字段与关联路径。

- **D2-1 查询字段有索引**：列表页的筛选/排序字段有对应索引（无索引的深分页排序 = Major）
- **D2-2 关联路径存在**：跨表查询所需的外键/关联字段在 DDL 中落地（缺 FK 字段 = Blocker）
- **D2-3 远程字段排序**：接口要求按 A 表字段排序却只 join 到 B 表 = Blocker
- **D2-4 冗余一致性**：为查询性能引入的冗余字段，有同步/更新的设计（无 = Major）

## 维度三：状态并发

- **D3-1 状态机闭环**：状态枚举完整，正向/逆向流转都有定义（逆向流转未定义 = Major）
- **D3-2 非法流转防护**：状态变更操作有前置状态校验（无校验可直接改 = Blocker）
- **D3-3 并发更新**：状态/计数等有竞争风险的字段，有乐观锁（version 列）或悲观锁设计（无 = Major）
- **D3-4 幂等**：重复提交/重复点击不会产生重复数据（无幂等键设计 = Blocker）

## 维度四：性能

- **D4-1 深分页**：大数据量列表有深分页/游标方案，不是 `LIMIT offset` 一路到底（无 = Major）
- **D4-2 导出**：导出/批量任务走专用接口或异步，不循环分页拼数据（R 层循环分页导出 = Blocker）
- **D4-3 N+1 查询**：列表接口是否隐含 N+1 查询风险（逐行查子表 = Major）
- **D4-4 大字段**：是否有把大文本/JSON 塞进高频查询表的反模式（= Major）

## 维度五：合规

- **D5-1 敏感字段脱敏**：手机号/身份证等敏感字段，接口响应有脱敏设计（无 = Blocker）
- **D5-2 硬编码枚举**：状态/类型等枚举未硬编码，有字典表或常量约定（硬编码 = Major）
- **D5-3 鉴权/租户隔离**：接口有鉴权与数据权限（tenant/机构）隔离设计（无 = Blocker）
- **D5-4 审计留痕**：关键操作（删除/导出/权限变更）有操作日志设计（无 = Major）

## 分级

| 级别 | 含义 | 门禁影响 |
|------|------|---------|
| Blocker | 开发会做错 / 上线必然整改 | 计入 `blockerCount`，触发 `PAUSE@design-blocker` |
| Major | 有风险但可带问题推进 | 报告列出，不阻塞 |
| Minor | 优化建议 | 报告列出 |
| Question | 待设计者/干系人确认 | 报告列出 |

## 迭代项目额外核对

- **E-1 兼容性**：增量变更是否破坏既有表结构（改既有列类型/删除列 = Blocker）
- **E-2 回归**：新增表/字段是否与既有同名表/字段冲突（= Blocker）
- **E-3 复用正确**：标注「复用」的表/接口是否真的与现状清单一致（= Major）
