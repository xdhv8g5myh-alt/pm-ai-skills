# PM 技能包 — 项目管理规范

> 本文件定义所有 pm-* 技能包共享的项目管理机制：项目目录骨架、产物索引、共享规范、编号体系、状态追踪、批次生命周期。每个技能包的 prompt.md 必须引用并遵守本文件。

---

## 一、项目目录骨架

每个项目的所有产物统一存放在 `output/[项目名]/` 下，首次执行任意技能包时自动创建：

```
output/[项目名]/
├── README.md                           # 项目产物索引（自动维护；文件名保持英文）
├── 项目规范.md                          # 共享规范文件（跨批次 append-only）
├── CLAUDE.md                           # 工程规格（§十三 自动生成；文件名保持英文）
├── 项目配置.md                          # 一次性初始化配置（§十三；入参非产物，不进产物索引）
├── .pm-state.json                      # 项目状态追踪文件（文件名保持不变）
│
├── 需求分析/                            # pm-analyze / pm-design-reverse 产物
│   ├── 需求分析报告.md                  # 全量分析报告
│   ├── 轻量分析-[日期].md               # 轻量分析（可多次）
│   └── 设计稿反推-[日期].md             # pm-design-reverse 补充产物（已有分析报告时）
│
├── 原型/                                # pm-prototype 产物
│   ├── 管理后台/                        # 按端类型分目录（admin / h5 / user-pc / miniapp）
│   │   ├── index.html                  # 导航页（文件名保持英文）
│   │   └── [中文页面名].html
│   ├── H5/
│   ├── 用户前台/
│   └── 小程序/
│
├── _公共资源/                           # 原型公共资源（vendor / theme / proto-utils）
│                                       # 原型页以 ../../_公共资源/ 相对引用
│                                       # pm-prototype 首次生成原型时从插件 assets/ 复制；
│                                       # pm-annotate 另补其标注资源（css / 引擎 / 数据）
│
├── 需求文档/                            # pm-prd 产物
│   ├── [项目名]-PRD-v1.0.md
│   ├── [项目名]-测试用例.md
│   ├── [项目名]-工时估算.md
│   ├── [项目名]-评审自查-[日期].md      # pm-review / pm-prd 步骤 3.6 产物
│   └── 变更单/                          # 变更单归档
│       └── 变更-[日期]-[功能名].md
│
├── 前端交付/                            # pm-deliver 产物
│   ├── package.json
│   ├── src/
│   └── ...
│
├── 设计/                                # 研发链 · 设计段（pm-design-*）
│   ├── [项目名]-功能详细设计.md          # pm-design-1-func
│   ├── [项目名]-数据库设计.md            # pm-design-2-db（新项目）
│   ├── [项目名]-数据库变更设计.md        # pm-design-2-db（迭代项目）
│   ├── 数据库/
│   │   ├── [项目名]-表结构.sql           # 新项目：全量建表
│   │   └── [项目名]-增量-[日期].sql      # 迭代项目：增量 DDL
│   └── 评审/
│       └── [项目名]-设计评审-[日期].md   # pm-design-3-review
│
├── 后端工程/                            # 研发链 · pm-dev-1-backend（Maven 工程）
│
├── 独立前端工程/                        # 研发链 · pm-dev-2-frontend（独立新工程，可选）
│
├── 测试/                                # 研发链 · pm-dev-3-test
│   └── [项目名]-单元测试报告-[日期].md
│
└── 代码审查/                            # 研发链 · pm-dev-4-codereview
    └── [项目名]-代码审查报告-[日期].md
```

> **命名约定**：产物目录与产物文件名一律中文；工具链/代码文件（`package.json`、`pom.xml`、`index.html`、`vite.config.ts`、`src/**`）与状态文件（`README.md`、`.pm-state.json`、`.pm-run.md`、`.pm-dev-run.md`）保持英文原名。中文命名的改造自 v1.5.0 起，**只对新项目生效，不迁移历史项目**。

### 目录创建规则

- 首次执行时检查 `output/[项目名]/` 是否存在，不存在则创建骨架
- 创建 `README.md` 和 `.pm-state.json` 初始文件
- 只创建当前技能需要的子目录（pm-analyze 只建 `需求分析/`，不建 `前端交付/`）
- **研发链（pm-design-* / pm-dev-*）独立运行时**：不要求 PM 链先跑完；若目录无
  README / 项目规范 / .pm-state.json，由 pm-design-1-func 自行初始化最小骨架。
  迭代项目复用已有 `后端工程/`、`设计/数据库/*-表结构.sql`，不重建

## 四、编号体系

所有产物中的功能点、测试用例使用统一编号，确保跨文档可引用：

| 前缀 | 含义 | 格式 | 使用场景 |
|------|------|------|---------|
| F | 功能 | F001, F002, ... | 分析报告功能清单 → PRD 功能章节 |
| T | 测试用例 | T001, T002, ... | 测试用例文档 |
| R | 接口 | R001, R002, ... | PRD 接口列表 → 项目规范.md |
| P | 页面 | P001, P002, ... | 原型页面列表 → PRD 页面章节 |
| C | 变更单 | C001, C002, ... | 变更单编号 |

### 编号分配规则

1. **连续递增**：每个前缀独立编号，从 001 开始
2. **跨批次不重置**：B2 的功能编号从 B1 最后一个编号后续编（B1 到 F012，B2 从 F013 开始）
3. **溯源标注**：变更功能必须标注原编号（如"F013 - 变更自 B1:F005"）
4. **pm-analyze 分配 F 编号**：功能清单中每条功能必须有 F 编号
5. **pm-prd 分配 T/R 编号**：测试用例和接口各自编号
6. **pm-prototype 分配 P 编号**：每个页面一个 P 编号
7. **研发链复用 F/R**：不新增前缀、不扩展 counters 类型。接 PM 链时只消费 PRD 已分配的
   F/R；独立跑（只有需求）或迭代时由 pm-design-1-func 自行分配/续编 F/R，写入
   `.pm-state.json` 顶层 `counters.F/R`
8. **pm-prd 分配 C 编号**：生成变更单时从 `counters.C + 1` 续编，并回写 `counters.C`
9. **测试用例编号一律用 `T` 前缀**（`T001`），**禁止** `TC-[模块]-[序号]` 之类变体

### 编号在文档中的使用示例

```markdown
## 功能清单（MoSCoW）

### Must Have
- [x] **F001 用户注册**：邮箱+手机号双通道注册。*理由：核心入口*
- [x] **F002 用户登录**：账号密码+短信验证码。*理由：核心入口*

### 测试用例
| 编号 | 关联功能 | 场景 | 操作 | 预期结果 |
|------|---------|------|------|---------|
| T001 | F001 | 正常注册 | 输入合法邮箱和密码 | 注册成功 |
| T002 | F001 | 邮箱重复 | 输入已注册邮箱 | 提示"邮箱已注册" |
```

### 状态追踪规则

1. **每个技能包启动时**：Read `.pm-state.json`，获取当前批次和计数器
2. **每个技能包完成后**：更新 pipeline 对应 step 的 status/completedAt/output/counters
3. **counters 全局递增**：新分配的 F/T/R/P 编号从 counters 当前值 +1 开始
4. **断点续做**：如果 `.pm-state.json` 中某步骤 status 为 `in_progress`，说明上次中断，提示用户是否续做

### 续做提示

当检测到上次中断时，向用户输出：

```
检测到项目"[项目名]"上次在 [步骤名] 阶段中断（开始于 [时间]）。
- 输入"继续"：从中断处继续
- 输入"重新开始"：重新执行该步骤
- 输入"跳过"：标记为完成，进入下一步
```

**规则**：
- 顶层字段 `devProjectType` ∈ `"new" | "iteration"`，首跑时写入、续做时读取；迭代项目加
  `devBaseline`（既有工程路径 / schema 路径 / 历史批次引用）。
- 条目 optional keys：`blockerCount`（3-review）、`reviewBlockerCount`（4-codereview）、
  `skipped`（2-frontend 跳过时）、`dependencySkipped`（用户强制跳过门禁时）。
- `counters` 类型闭表 `{F,T,R,P,C}` 不变。接 PM 链时 devPipeline 条目 `counters` 恒 `{}`；
  独立跑/迭代时分配的 F/R 写入**顶层** `counters.F/R`（非条目内）。
- 时间戳一律 UTC ISO-8601 结尾 `Z`，无值写 `null`。
- `batchStatus` 不受研发链影响；研发链全部 PASS 时仅在 `.pm-dev-run.md` 置「已完成」。

### pipeline 步名闭表（PM 链）

`pipeline[]` 允许的 step 名**只有**以下 6 个，按拓扑顺序：

```
pm-analyze → pm-prototype → pm-prd → pm-review → pm-annotate → pm-deliver
```

- **可选步**：`pm-review`（仅执行了评审自查时有条目）与 `pm-annotate`（`--skip-annotate` 时无条目）。
  缺条目 = 未执行，**不算异常**，不要补占位条目。
- `pm-review` 在 pm-prd 步骤 3.6 内部触发，位置固定在 `pm-prd` 之后。
- **optional keys 按链隔离，不串读**：
  - PM 链条目 —— `blockerCount`（pm-analyze）、`reviewBlockerCount`（pm-review / pm-prd 的评审自查结果）
  - 研发链条目 —— `blockerCount`（pm-design-3-review）、`reviewBlockerCount`（pm-dev-4-codereview）、
    `skipped`（2-frontend 跳过）、`dependencySkipped`（用户强制跳过门禁）

## 六、产物依赖矩阵（强制门禁）

每个技能包启动时**必须检查**前置产物是否存在，不满足则**停止执行并提示用户**，禁止跳过。

| 当前技能 | 前置依赖 | 检查文件 | 不满足时行为 |
|----------|---------|---------|------------|
| pm-analyze | 无（入口技能） | — | 直接执行 |
| pm-design-reverse | 无（入口技能） | — | 直接执行 |
| pm-prototype | pm-analyze 已完成 | `output/[项目名]/需求分析/需求分析报告.md` 存在 | ❌ 停止，提示"请先执行 pm-analyze 完成需求分析" |
| pm-prd | pm-analyze 或 pm-design-reverse 已完成 | `需求分析/需求分析报告.md` **或** `需求分析/设计稿反推-*.md` 存在 | ❌ 停止，提示"请先执行 pm-analyze 或 pm-design-reverse" |
| pm-review | pm-prd 已完成（或用户指定外部 PRD） | `需求文档/*-PRD-*.md` 存在 | ❌ 停止，提示"请先执行 pm-prd 生成 PRD" |
| pm-deliver | pm-prototype 已完成 | `output/[项目名]/原型/[端]/` 下至少有 1 个 HTML 文件 | ❌ 停止，提示"请先执行 pm-prototype 生成原型" |
| pm-annotate | pm-prototype 已完成 | `output/[项目名]/原型/[端]/` 下至少有 1 个**非**"标注版"HTML 文件 | ❌ 停止，提示"请先执行 pm-prototype 生成原型" |
| pm-design-1-func | 无硬门禁（入口） | 有 PRD（`需求文档/*.md` 或 `--prd`）或有需求内容；无 `.pm-state.json` 则先初始化 | 直接执行 |
| pm-design-2-db | pm-design-1-func 完成 | `设计/[项目名]-功能详细设计.md` 存在 + devPipeline `pm-design-1-func`=completed | ❌ 停止，提示"请先执行 pm-design-1-func" |
| pm-design-3-review | 1-func + 2-db 完成 | 功能详细设计.md + 表结构/增量 SQL 均存在 | ❌ 停止，提示"请先完成功能详细设计与数据库设计" |
| pm-dev-1-backend | 设计段完成 + 评审无未解决 Blocker | 功能详细设计.md + 表结构/增量 SQL 存在；devPipeline 中 `pm-design-3-review` 条目 `blockerCount` 为 0 或缺失 | ❌ 停止，提示"请先完成设计评审（Blocker 已解决）" |
| pm-dev-2-frontend | 后端完成 | `后端工程/pom.xml` 存在 + devPipeline `pm-dev-1-backend`=completed | ❌ 停止，提示"请先执行 pm-dev-1-backend" |
| pm-dev-3-test | 后端完成 | `后端工程/` 存在 | ❌ 停止，提示"请先执行 pm-dev-1-backend" |
| pm-dev-4-codereview | 后端完成 | `后端工程/` 存在 | ❌ 停止，提示"请先执行 pm-dev-1-backend" |

### 依赖检查执行规则

1. **硬门禁**：依赖检查失败时必须停止，不得"降级执行"或"边做边等"
2. **检查时机**：在步骤 0（读取项目上下文）之后、步骤 1（判断模式）之前执行
3. **`.pm-state.json` 辅助检查**：除文件存在性外，同时检查 `.pm-state.json` 中对应 pipeline step 的 status 是否为 `completed`
4. **用户强制跳过**：如果用户明确说"跳过依赖检查"或"我有自己的分析文档"，可跳过门禁，但必须在本步**所属链的条目内**记录 `"dependencySkipped": true`（PM 链写 `pipeline[]`，研发链写 `devPipeline[]`）

## 七、规范引用铁律

所有技能包执行前必须读取共享规范文件，确保产物与已有决策一致。

### 强制读取顺序

```
1. `output/[项目名]/CLAUDE.md`（§十三 生成，如存在）→ 提取技术栈、组件约定、业务术语；若其中声明了「参见 docs/component-spec.md」等自定义组件文档，一并读取（只读，不回写）。**项目内没有时再看当前目录的 CLAUDE.md（只读，不回写）；两处都有以项目内为准**
2. output/[项目名]/项目规范.md（如存在）→ 提取已有技术决策、接口清单、组件约定
3. output/[项目名]/.pm-state.json → 获取批次、计数器、pipeline 状态
```

### 铁律

1. **先读后做**：未读取 项目规范.md 就开始生成产物 → 违规。每个技能包的 prompt.md 步骤 0 必须包含读取规范的动作
2. **一致性校验**：如果生成的产物与 项目规范.md 中已有决策矛盾（如接口路径冲突、组件约定不同），必须向用户报告冲突并等待决策
3. **反向沉淀**：每个技能包完成后，如果产生了新的可复用规范（如新发现的组件约定、接口规范），必须 append 到 项目规范.md；若 `CLAUDE.md` 存在，同步追加到其「迭代记录」节，保持两份规范一致，避免下次读到过时的 CLAUDE.md

## 八、变更溯源体系

跨批次变更时，必须标注功能的变更来源，确保产物可追溯。

### 变更溯源规则

1. **变更功能必须溯源**：当 B2+ 批次的功能是对历史批次功能的修改时，必须标注 `变更自 B[N]:F[XXX]`
2. **功能清单标注格式**：
   ```markdown
   - [ ] **F015 用户导出优化**：增加异步导出队列。*变更自 B1:F008* | *理由：大数据量性能*
   ```
3. **PRD 中的变更标注**：变更功能在 PRD 中独立成节，标题格式 `### F015 用户导出优化（变更自 B1:F008）`
4. **测试用例关联**：变更功能的测试用例必须包含回归测试项，验证原功能不受影响
5. **项目规范.md 记录**：在"技术决策"章节追加变更批次的决策记录

### 变更类型

| 类型 | 标注 | 说明 |
|------|------|------|
| 新增 | `新增于 B[N]` | 全新功能 |
| 修改 | `变更自 B[M]:F[XXX]` | 对已有功能的修改 |
| 删除 | `删除 B[M]:F[XXX]` | 废弃已有功能 |
| 拆分 | `拆分自 B[M]:F[XXX]` | 将一个功能拆为多个 |

## 九、多格式需求抽取

pm-analyze 支持从多种格式的输入中提取需求信息。

### 支持的输入格式

| 格式 | 处理方式 | 适用场景 |
|------|---------|---------|
| 纯文本 / Markdown | 直接分析 | 会议纪要、需求描述 |
| PDF | Read 工具读取，提取文本内容 | 正式需求文档 |
| 图片（PNG/JPG/截图） | Read 工具读取（多模态），识别其中的文字和界面元素 | 原型截图、竞品截图、手绘草图 |
| Excel/CSV | Read 工具读取，提取表格结构 | 功能清单、数据字典 |
| 已有代码文件 | Read 工具读取，提取业务逻辑 | 逆向分析已有系统 |

### 抽取规则

1. **格式识别**：用户提供文件路径时，根据扩展名自动识别格式
2. **结构化抽取**：从非结构化输入中提取→ 用户角色、功能需求、业务规则、约束条件
3. **来源标注**：分析报告中每条功能必须标注信息来源（如"来源：需求文档 P3"、"来源：竞品截图"）
4. **多源合并**：当用户提供多个输入文件时，合并分析，冲突处列入待澄清问题

## 十、门禁暂停机制

在关键节点设置门禁，防止带着未解决问题继续推进。

### 门禁点

| 触发时机 | 检查条件 | 暂停行为 |
|---------|---------|---------|
| pm-analyze 完成后 | `需求分析/需求分析报告.md` 第 7 章中「风险等级=高 **且** 状态=待确认」的问题数 > 0 | 记 `PAUSE@analyze-blocker`，输出 Blocker 清单，暂停（**标记由 pm-autopilot 写**） |
| pm-prototype 启动前 | 同上（第 7 章「风险等级=高 且 状态=待确认」的问题数 > 0） | 提示 + 用户确认「继续」可带问题推进（**软门禁**，不硬阻止） |
| pm-prd 完成后 | PRD 中标注了"待确认"项 | 提醒用户确认，但不强制暂停 |
| pm-review 后 | 评审自查 Blocker > 0 | 提醒用户，不强制暂停（**软门禁**） |
| pm-annotate 后 | `原型/[端]/` 下无 `*-标注版.html`，或原原型被覆盖 | 记 FAIL，暂停（`--skip-annotate` 时记跳过） |
| pm-deliver 启动前 | PRD 不存在或未标注批次 | 阻止启动 |
| pm-design-3-review 后 | 设计评审 Blocker > 0 | 记 `PAUSE@design-blocker`，输出 Blocker 清单，暂停 |
| pm-dev-1-backend 后 | `后端工程/` 无 pom.xml 或编译失败 | 记 FAIL，暂停 |
| pm-dev-2-frontend 后 | `独立前端工程/` 无 package.json（未 `--skip-frontend`） | 记 FAIL，暂停 |
| pm-dev-3-test 后 | 覆盖率未达标或单测未通过 | 记 FAIL，暂停 |
| pm-dev-4-codereview 后 | 严重问题 > 0 | 记 `PAUSE@codereview`（报告完成，阻塞下游），暂停（**标记由 pm-dev-autopilot 写**；技能自身只在报告/摘要标注「阻塞下游」） |

> **研发链门禁独立于 PM 链**：`PAUSE@design-blocker` / `PAUSE@codereview` 与
> `PAUSE@analyze-blocker` 平行，各自只影响本链。研发链的 Blocker 属「门禁暂停」，
> **独立于步骤 STATUS**（评审/审查产物齐全即返回 PASS）。

### Blocker 状态模型

| 状态 | 说明 | 门禁影响 |
|------|------|---------|
| 待确认 | 问题已提出，等待干系人回答 | 计入 Blocker 遗留数，触发暂停 |
| 已确认 | 干系人已回答，结论已采纳 | 不计入遗留数 |
| 已关闭 | 问题已解决或不再相关 | 不计入遗留数 |

> **承载要求**：`需求分析报告.md` 第 7 章与设计评审报告的 Blocker 表**必须带「状态」列**
> （取值即上表三值，默认「待确认」）。各技能统计 Blocker 遗留数时**只计「待确认」的行**；
> 重跑时读上一份报告回填已变更的状态。**报告没有「状态」列 = 门禁不可判定**，属规范违规。

### 暂停后恢复

当门禁暂停后，用户处理完 Blocker 重新执行技能包时：
1. 读取 `.pm-state.json`，检测上次暂停点
2. 重新检查门禁条件
3. 条件满足 → 从暂停点继续
4. 条件仍不满足 → 再次暂停，输出未解决的 Blocker 清单
5. **评审类 Blocker**（`design-blocker` / `codereview`）：修复后必须**重跑对应评审技能生成新报告**，
   再按新报告 Blocker 表中「待确认」行数判定。旧报告不会自动更新——直接 re-check 旧报告会导致**永远无法解除**
6. **用户确认放行**：用户明确表示带问题推进时，在 run 文件备注记「已确认放行（用户 [时间]）」；
   后续启动检测到该标记则不再重复暂停

## 十一、批次生命周期

### 批次状态流转

```
新建 (new)
  ↓ 开始执行任意技能包
进行中 (in_progress)
  ↓ PM 链所有非跳过步完成 或 用户手动触发
已完成 (completed)
  ↓ 用户说"冻结批次"
已冻结 (frozen)
  ↓ 用户说"归档批次"
已归档 (archived)

特殊流转：
已冻结 → 进行中（用户说"解冻批次"）
```

### 新批次创建

当用户对一个已有项目发起新的需求时：

1. 检查当前批次状态
2. 如果当前批次是 `completed` 或 `frozen`，自动创建新批次（B2, B3, ...）
3. 新批次的编号计数器从上一批次末尾续编
4. 变更单自动标注"变更自 B[N]:F[XXX]"

### 批次命令

| 触发词 | 效果 |
|--------|------|
| 冻结批次 / 冻结[项目名] | 当前批次 → frozen，禁止修改产物 |
| 解冻批次 | frozen → in_progress，允许修改 |
| 归档批次 | frozen → archived，产物只读 |
| 新批次 / 开始迭代 | 创建新批次，编号续编 |
| 查看批次 / 批次状态 | 输出当前项目的批次列表和状态 |

### 批次信息在产物中的标注

每个产物文件的头部必须标注批次信息：

```markdown
> 批次：B1 | 生成时间：2026-09-26 14:30 | 技能：pm-analyze v1.5.0
```

变更单额外标注来源批次：

```markdown
> 批次：B2 | 变更自：B1 | 涉及功能：F005, F008
```

## 十二、历史参考（研发链跨项目一致性）

研发链在动手设计前，先扫描参考目录，建立「可复用资产基线」，优先复用历史约定，保持跨项目一致。

### 参考目录

- 默认 `pm-ai-projects/output/`（各历史项目的产物根），可用 `--ref <路径>` 覆盖
- 也含**当前项目自身历史**（迭代时参考自己上一批次的设计/代码/DDL）

### 可复用资产清单（扫描目标）

| 资产 | 来源 | 用途 |
|------|------|------|
| 表/字段命名约定 | 历史 `设计/数据库/*-表结构.sql` | 复用同义表/字段名（`t_` 前缀、snake_case） |
| 通用实体 | 历史 `设计/*-数据库设计.md`、`后端工程/` entity | 复用用户/部门/字典等公共实体 |
| 错误码分段 | 历史 `设计/*-功能详细设计.md`、`项目规范.md` | 新接口错误码不冲突 |
| 响应/分页/鉴权约定 | 历史 `后端工程/` 的 `Result<T>`、分页、JWT | 沿用统一响应与鉴权模式 |
| 接口风格 | 历史 `项目规范.md`「接口清单」、`后端工程/` controller | RESTful 路径/动词一致 |
| 实体/DDL 映射 | 历史 `设计/*-数据库设计.md` 的字段映射表 | 复用具名规则 |

### 规则

1. **软参考，不阻塞**：参考目录找不到资产就跳过，不报错、不中断
2. **复用留痕**：功能详细设计中注明「参考来源」（哪个历史项目的哪个文件/约定）
3. **不自动改写历史项目**：只读，绝不回写参考项目
4. **冲突优先自身**：当前项目 项目规范.md 已有决策优先于历史参考

### 消费规则（两条链分工）

|--------|---------------------|---------------------------|

### CLAUDE.md 自动生成

配置含前后端工程时，从实际工程**探测提取**（不脑补）生成 `output/[项目名]/CLAUDE.md`：

```markdown
# 项目：[系统名]

## 技术栈
- 前端：（框架/组件库，探测自 package.json）
- 后端：（框架/ORM/DB，探测自 pom.xml）
- 常用命令：（探测自 package.json scripts / pom.xml）

## 已有模块（避免 AI 推荐已存在的功能）
- （探测自 src 目录结构）

## 接口规范
- baseURL / 响应格式 / 分页（探测或来自配置「8. 备注约束」）

## 迭代记录（累积知识，AI 每次迭代反向沉淀到这里）
- （每次迭代产生的新技术决策 / 组件约定 / 接口规范追加于此，只追加不删除）
```

### 规则

1. **配置文档是入参不是产物**：不进 README 产物索引（同 `.pm-dev-run.md`），AI 不回写
2. **无配置不阻塞**：软参考语义，找不到/不填就跳过
3. **幂等**：工程/脚本已就位不重复拉取；CLAUDE.md 已存在不覆盖（仅补缺）
4. **消费留痕**：功能详细设计「参考来源」注明「配置：项目配置.md」
5. **过时提示**：读配置时若发现信息与实际不符（工程路径 / 分支 / DDL 已变），提示用户更新配置，不自行改写
6. **配置节 8「备注约束」必须被研发链消费**：pm-design-1-func 步骤 0.4 须逐条 append 到 `项目规范.md`
   「技术决策」（不覆盖既有行），其中的接口规范项（baseURL / 响应格式 / 分页）并入 `CLAUDE.md`「接口规范」节。
   研发链**独立运行**（不经 pm-analyze）时这是**唯一**的约束入口——漏消费会导致设计违反用户强制约束
