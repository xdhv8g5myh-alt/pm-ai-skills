# PM 技能包 — 项目管理规范

> 本文件定义所有 pm-* 技能包共享的项目管理机制：项目目录骨架、产物索引、共享规范、编号体系、状态追踪、批次生命周期。每个技能包的 prompt.md 必须引用并遵守本文件。

---

## 一、项目目录骨架

每个项目的所有产物统一存放在 `output/[项目名]/` 下，首次执行任意技能包时自动创建：

```
output/[项目名]/
├── README.md                           # 项目产物索引（自动维护）
├── project-spec.md                     # 共享规范文件（跨批次 append-only）
├── .pm-state.json                      # 项目状态追踪文件
│
├── analysis/                           # pm-analyze 产物
│   ├── analysis-report.md              # 全量分析报告
│   └── quick-analysis-[日期].md        # 轻量分析（可多次）
│
├── prototypes/                         # pm-prototype 产物
│   ├── admin/                          # 按端类型分目录
│   │   ├── index.html
│   │   └── [页面名].html
│   ├── h5/
│   ├── user-pc/
│   └── miniapp/
│
├── prd/                                # pm-prd 产物
│   ├── [项目名]-PRD-v1.0.md
│   ├── [项目名]-test-cases.md
│   ├── [项目名]-estimate.md
│   └── changes/                        # 变更单归档
│       └── change-[日期]-[功能名].md
│
└── vue/                                # pm-deliver 产物
    ├── package.json
    ├── src/
    └── ...
```

### 目录创建规则

- 首次执行时检查 `output/[项目名]/` 是否存在，不存在则创建骨架
- 创建 `README.md` 和 `.pm-state.json` 初始文件
- 只创建当前技能需要的子目录（pm-analyze 只建 analysis/，不建 vue/）

3. README.md 不可手动编辑"产物清单"之外的内容

## 四、编号体系

所有产物中的功能点、测试用例使用统一编号，确保跨文档可引用：

| 前缀 | 含义 | 格式 | 使用场景 |
|------|------|------|---------|
| F | 功能 | F001, F002, ... | 分析报告功能清单 → PRD 功能章节 |
| T | 测试用例 | T001, T002, ... | 测试用例文档 |
| R | 接口 | R001, R002, ... | PRD 接口列表 → project-spec.md |
| P | 页面 | P001, P002, ... | 原型页面列表 → PRD 页面章节 |
| C | 变更单 | C001, C002, ... | 变更单编号 |

### 编号分配规则

1. **连续递增**：每个前缀独立编号，从 001 开始
2. **跨批次不重置**：B2 的功能编号从 B1 最后一个编号后续编（B1 到 F012，B2 从 F013 开始）
3. **溯源标注**：变更功能必须标注原编号（如"F013 - 变更自 B1:F005"）
4. **pm-analyze 分配 F 编号**：功能清单中每条功能必须有 F 编号
5. **pm-prd 分配 T/R 编号**：测试用例和接口各自编号
6. **pm-prototype 分配 P 编号**：每个页面一个 P 编号

### 编号在文档中的使用示例

```markdown
## 功能清单（MoSCoW）

### Must Have
- [x] **F001 用户注册**：邮箱+手机号双通道注册。*理由：核心入口*
- [x] **F002 用户登录**：账号密码+短信验证码。*理由：核心入口*

### 测试用例
| 编号 | 关联功能 | 场景 | 操作 | 预期结果 |
|------|---------|------|------|---------|
| T001 | F001 | 正常注册 | 输入合法邮箱和密码 | 注册成功 |
| T002 | F001 | 邮箱重复 | 输入已注册邮箱 | 提示"邮箱已注册" |
```

## 五、状态追踪 .pm-state.json

`output/[项目名]/.pm-state.json` 记录项目执行状态，支持断点续做：

```json
{
  "project": "培训管理系统",
  "created": "2026-09-26T14:00:00Z",
  "currentBatch": "B1",
  "batchStatus": "in_progress",
  "counters": {
    "F": 12,
    "T": 36,
    "R": 8,
    "P": 8,
    "C": 0
  },
  "pipeline": [
    {
      "step": "pm-analyze",
      "status": "completed",
      "startedAt": "2026-09-26T14:00:00Z",
      "completedAt": "2026-09-26T14:15:00Z",
      "output": "analysis/analysis-report.md",
      "counters": { "F": 12 }
    },
    {
      "step": "pm-prototype",
      "status": "completed",
      "startedAt": "2026-09-26T14:30:00Z",
      "completedAt": "2026-09-26T15:00:00Z",
      "output": "prototypes/admin/",
      "counters": { "P": 8 }
    },
    {
      "step": "pm-prd",
      "status": "in_progress",
      "startedAt": "2026-09-26T15:30:00Z",
      "completedAt": null,
      "output": null,
      "counters": {}
    },
    {
      "step": "pm-deliver",
      "status": "pending",
      "startedAt": null,
      "completedAt": null,
      "output": null,
      "counters": {}
    }
  ],
  "batches": [
    {
      "id": "B1",
      "name": "初始版本",
      "status": "in_progress",
      "createdAt": "2026-09-26T14:00:00Z",
      "frozenAt": null,
      "archivedAt": null,
      "counterRanges": {
        "F": [1, 12],
        "T": [1, 36],
        "P": [1, 8]
      }
    }
  ]
}
```

### 状态追踪规则

1. **每个技能包启动时**：Read `.pm-state.json`，获取当前批次和计数器
2. **每个技能包完成后**：更新 pipeline 对应 step 的 status/completedAt/output/counters
3. **counters 全局递增**：新分配的 F/T/R/P 编号从 counters 当前值 +1 开始
4. **断点续做**：如果 `.pm-state.json` 中某步骤 status 为 `in_progress`，说明上次中断，提示用户是否续做

### 续做提示

当检测到上次中断时，向用户输出：

```
检测到项目"[项目名]"上次在 [步骤名] 阶段中断（开始于 [时间]）。
- 输入"继续"：从中断处继续
- 输入"重新开始"：重新执行该步骤
- 输入"跳过"：标记为完成，进入下一步
```

## 六、产物依赖矩阵（强制门禁）

每个技能包启动时**必须检查**前置产物是否存在，不满足则**停止执行并提示用户**，禁止跳过。

| 当前技能 | 前置依赖 | 检查文件 | 不满足时行为 |
|----------|---------|---------|------------|
| pm-analyze | 无（入口技能） | — | 直接执行 |
| pm-prototype | pm-analyze 已完成 | `output/[项目名]/analysis/analysis-report.md` 存在 | ❌ 停止，提示"请先执行 pm-analyze 完成需求分析" |
| pm-prd | pm-analyze 已完成 | `output/[项目名]/analysis/analysis-report.md` 存在 | ❌ 停止，提示"请先执行 pm-analyze 完成需求分析" |
| pm-deliver | pm-prototype 已完成 | `output/[项目名]/prototypes/[端]/` 下至少有 1 个 HTML 文件 | ❌ 停止，提示"请先执行 pm-prototype 生成原型" |

### 依赖检查执行规则

1. **硬门禁**：依赖检查失败时必须停止，不得"降级执行"或"边做边等"
2. **检查时机**：在步骤 0（读取项目上下文）之后、步骤 1（判断模式）之前执行
3. **`.pm-state.json` 辅助检查**：除文件存在性外，同时检查 `.pm-state.json` 中对应 pipeline step 的 status 是否为 `completed`
4. **用户强制跳过**：如果用户明确说"跳过依赖检查"或"我有自己的分析文档"，可跳过门禁，但必须在 `.pm-state.json` 中记录 `"dependencySkipped": true`

## 七、规范引用铁律

所有技能包执行前必须读取共享规范文件，确保产物与已有决策一致。

### 强制读取顺序

```
1. CLAUDE.md（如存在）→ 提取技术栈、组件约定、业务术语
2. output/[项目名]/project-spec.md（如存在）→ 提取已有技术决策、接口清单、组件约定
3. output/[项目名]/.pm-state.json → 获取批次、计数器、pipeline 状态
```

### 铁律

1. **先读后做**：未读取 project-spec.md 就开始生成产物 → 违规。每个技能包的 prompt.md 步骤 0 必须包含读取规范的动作
2. **一致性校验**：如果生成的产物与 project-spec.md 中已有决策矛盾（如接口路径冲突、组件约定不同），必须向用户报告冲突并等待决策
3. **反向沉淀**：每个技能包完成后，如果产生了新的可复用规范（如新发现的组件约定、接口规范），必须 append 到 project-spec.md

## 八、变更溯源体系

跨批次变更时，必须标注功能的变更来源，确保产物可追溯。

### 变更溯源规则

1. **变更功能必须溯源**：当 B2+ 批次的功能是对历史批次功能的修改时，必须标注 `变更自 B[N]:F[XXX]`
2. **功能清单标注格式**：
   ```markdown
   - [ ] **F015 用户导出优化**：增加异步导出队列。*变更自 B1:F008* | *理由：大数据量性能*
   ```
3. **PRD 中的变更标注**：变更功能在 PRD 中独立成节，标题格式 `### F015 用户导出优化（变更自 B1:F008）`
4. **测试用例关联**：变更功能的测试用例必须包含回归测试项，验证原功能不受影响
5. **project-spec.md 记录**：在"技术决策"章节追加变更批次的决策记录

### 变更类型

| 类型 | 标注 | 说明 |
|------|------|------|
| 新增 | `新增于 B[N]` | 全新功能 |
| 修改 | `变更自 B[M]:F[XXX]` | 对已有功能的修改 |
| 删除 | `删除 B[M]:F[XXX]` | 废弃已有功能 |
| 拆分 | `拆分自 B[M]:F[XXX]` | 将一个功能拆为多个 |

## 九、多格式需求抽取

pm-analyze 支持从多种格式的输入中提取需求信息。

### 支持的输入格式

| 格式 | 处理方式 | 适用场景 |
|------|---------|---------|
| 纯文本 / Markdown | 直接分析 | 会议纪要、需求描述 |
| PDF | Read 工具读取，提取文本内容 | 正式需求文档 |
| 图片（PNG/JPG/截图） | Read 工具读取（多模态），识别其中的文字和界面元素 | 原型截图、竞品截图、手绘草图 |
| Excel/CSV | Read 工具读取，提取表格结构 | 功能清单、数据字典 |
| 已有代码文件 | Read 工具读取，提取业务逻辑 | 逆向分析已有系统 |

### 抽取规则

1. **格式识别**：用户提供文件路径时，根据扩展名自动识别格式
2. **结构化抽取**：从非结构化输入中提取→ 用户角色、功能需求、业务规则、约束条件
3. **来源标注**：分析报告中每条功能必须标注信息来源（如"来源：需求文档 P3"、"来源：竞品截图"）
4. **多源合并**：当用户提供多个输入文件时，合并分析，冲突处列入待澄清问题

## 十、门禁暂停机制

在关键节点设置门禁，防止带着未解决问题继续推进。

### 门禁点

| 触发时机 | 检查条件 | 暂停行为 |
|---------|---------|---------|
| pm-analyze 完成后 | 待澄清问题中 Blocker 数 > 0 | 暂停流程，提示用户处理 Blocker |
| pm-prototype 启动前 | analysis-report.md 中 Blocker 未全部标记为 ✅ | 阻止启动，提示用户先解决 Blocker |
| pm-prd 完成后 | PRD 中标注了"待确认"项 | 提醒用户确认，但不强制暂停 |
| pm-deliver 启动前 | PRD 不存在或未标注批次 | 阻止启动 |

### Blocker 状态模型

| 状态 | 说明 | 门禁影响 |
|------|------|---------|
| 待确认 | 问题已提出，等待干系人回答 | 计入 Blocker 遗留数，触发暂停 |
| 已确认 | 干系人已回答，结论已采纳 | 不计入遗留数 |
| 已关闭 | 问题已解决或不再相关 | 不计入遗留数 |

### 暂停后恢复

当门禁暂停后，用户处理完 Blocker 重新执行技能包时：
1. 读取 `.pm-state.json`，检测上次暂停点
2. 重新检查门禁条件
3. 条件满足 → 从暂停点继续
4. 条件仍不满足 → 再次暂停，输出未解决的 Blocker 清单

## 十一、批次生命周期

### 批次状态流转

```
新建 (new)
  ↓ 开始执行任意技能包
进行中 (in_progress)
  ↓ 全部4步完成 或 用户手动触发
已完成 (completed)
  ↓ 用户说"冻结批次"
已冻结 (frozen)
  ↓ 用户说"归档批次"
已归档 (archived)

特殊流转：
已冻结 → 进行中（用户说"解冻批次"）
```

### 新批次创建

当用户对一个已有项目发起新的需求时：

1. 检查当前批次状态
2. 如果当前批次是 `completed` 或 `frozen`，自动创建新批次（B2, B3, ...）
3. 新批次的编号计数器从上一批次末尾续编
4. 变更单自动标注"变更自 B[N]:F[XXX]"

### 批次命令

| 触发词 | 效果 |
|--------|------|
| 冻结批次 / 冻结[项目名] | 当前批次 → frozen，禁止修改产物 |
| 解冻批次 | frozen → in_progress，允许修改 |
| 归档批次 | frozen → archived，产物只读 |
| 新批次 / 开始迭代 | 创建新批次，编号续编 |
| 查看批次 / 批次状态 | 输出当前项目的批次列表和状态 |

### 批次信息在产物中的标注

每个产物文件的头部必须标注批次信息：

```markdown
> 批次：B1 | 生成时间：2026-09-26 14:30 | 技能：pm-analyze v2.0.0
```

变更单额外标注来源批次：

```markdown
> 批次：B2 | 变更自：B1 | 涉及功能：F005, F008
```
